## 1. The assignment (verbatim intent)

Build a small **RAG pipeline over 2–3 Indian construction documents of different types** that answers questions
**with citations back to the source**, plus **a fine-tuning element** (a fine-tuned/adapted model, classifier,
extractor, or similar). The reviewers care most about **reasoning, assumptions, decision-making, how the work is
tested and evaluated**. It is roughly **one day of work**. Free and open-source tools are fine. It must include a
**run file**: setup steps and how to ask a question. It is for a job application followed by an interview,
so it is not a production system.

**Hard requirement from the user:** the whole stack must be **free** and **easy for the invigilator to run** on their machine.

### 5b. Plan changes agreed before Phase 5 (2026-10-08)
A project review (PM + senior-dev view) found six points; the user decided:
- **No fallback to the base model (simplest fix).** Embeddings only make sense with the model that made them, and `index_meta.json` already records that model, which the app loads. So: rebuild the committed index with whichever model ships; if the Hugging Face download fails, the app stops with a clear message. The base-vs-fine-tuned eval embeds the chunks for each model **in memory** (~30 s each), no second index file. (Rejected: per-model embedding files, more machinery than needed.)
- **Gold wording is mixed and tagged** (`wording: natural | document`), reported separately. Natural wording shows whether fine-tuning helps; document wording keeps easy lookups honest. Decided before training, so it isn't tuned to favour the fine-tune.
- **Two retrieval scores:** *found* (at least one evidence passage retrieved) and *fully supported* (all evidence passages reach the LLM, e.g. Table 28 **and** Amd 2 item 10).
- **Gold references can't silently break:** every evidence entry stores chunk id + section + PDF pages + a verbatim quote; `eval/gold.py validate` checks all four against `chunks.jsonl`, and `tests/test_gold.py` runs it. Chunking is frozen once the gold set is.
- **Checking sheet for the user:** `eval/gold_review.md`, generated from the JSONL (question, expected answer, PDF + printed page, quote), about a minute per question.
- **Training data trimmed:** 2 questions per chunk (~900 candidates), not 3–4. Time depends on the number of LLM calls (one per chunk), not questions per chunk. Small trial (~30 chunks) read first, then the full run in the background.
- **Small-generator limits** (wide-table cells, boundary conditions, over-citing) go in the write-up as known limits; an extra bigger-model eval row only if time allows.

### Chunk model (`src/schema.py`)
`Chunk(chunk_id, doc_id, doc_title, section, text, pdf_pages, printed_pages, title, part, covers, is_amendment, amends, source, parent)`
- `breadcrumb` = `doc_title > part > section - title`. `index_text` = breadcrumb + text. **Embedding and BM25 both use `index_text`**, so short chunks inherit context.
- `citation` looks like `CPWD GCC 2020, Clause 10CC, p. 28 (PDF 30)`. Both the printed and the PDF page are kept. Amendments have no printed page, so they cite as `PDF p. 65-66`.
- `covers` = provision ids inside the chunk (e.g. `["Cl. 6.2.2.8","Cl. 6.2.2.9"]`, `["Table 28"]`). It is matched against amendments' `amends`.
- `parent` = for one part of a split curated table, the whole table's name (`"Table 2"`); empty otherwise. Used by sibling expansion. It isn't part of `index_text`, so adding it didn't change the embeddings.
- Chunk size limit: **400 tokens of body** (`MAX_CHUNK_TOKENS`), counted with bge-small's tokenizer (`token_count` in `text.py`). Breadcrumbs take ≤ ~60 tokens (`BREADCRUMB_TOKEN_RESERVE = 64`), so breadcrumb + body + [CLS]/[SEP] stays ≤ 512 (`EMBED_MAX_TOKENS`); `build.py` enforces this. A tiny tail (< 50 tokens, `MIN_TAIL_TOKENS`) is folded into the previous window. Largest chunk after the fix: 504 tokens (a Table 2 part).

## 8. Known limitations (to go in DECISIONS.md)
- IS 875: on a few pages (≈ PDF 41–42) the OCR interleaves the two columns, so some sentences are out of order and 6.3.2.4 is detected before 6.3.2.3.
- IS 875: the OCR lost some table headings (Tables 12, 14, 18, 19, 22, 26, 32). Their text is absorbed into the previous table's chunk (labelled with that table's name). For the ones that amendments target, `ABSORBED_PROVISIONS` makes the amendment attach anyway (see below). The remaining table chunks are OCR-noisy; only the curated Tables 1, 2 and 28 and Appendix A are reliable.
- CPWD: the first-aid list inside Model Rule 3 skews item labels for 2 chunks (pages are still correct). Formulas (10CA/10CC) extract imperfectly.
- Ssangyong: long paragraphs that quote other judgments (¶17, 33, 39–41, 44) become many "part i/n" chunks.
- Hand-curated content doesn't scale (scale path: layout/vision OCR plus document versioning).
- **City names (decided):** Appendix A uses 1987 names (Madras, Bombay, Calcutta…). The transcription keeps them as printed; at build time the modern name is added **inline in square brackets** from the separate `data/curated/place_aliases.yaml` ("Madras [now Chennai] 50" plus a legend line saying brackets are curator additions), so "wind speed in Chennai" both retrieves the chunk and gets answered reliably (see the "Old city names" entry below). Trade-off: it's added text, not from the PDF (marked `source: curated`). The scalable alternative is a query-time alias list. A city that isn't in Appendix A at all can only be read off the Fig. 1 map, which is an image and isn't indexed, so the system should answer "not found". **To do:** add a Chennai question and an unlisted-city question to the gold set.
- **Corpus scope:** answers come from IS 875-3:**1987 with Amd 1–3** only. A newer edition exists, but it isn't in the corpus. Neither the system nor the docs should describe it or call the 1987 values "current" (to be stated in the README/UI banner).
- `LOW_CONFIDENCE_COSINE` is calibrated on only 7 unanswerable questions: **0.51** with the fine-tuned model flags 6/7 unanswerable and 1/26 answerable (the base model's 0.55 flagged nothing). It is advisory; the LLM still decides "not found" itself.
- **Amendments whose target no chunk covered (fixed 2026-10-08):** 7 amendment items target Tables 12, 14, 19, 32 and Fig. 13, whose headings the OCR lost, so retrieval never attached them. Host = provision + text signature, because signatures alone match other chunks too. Verified: each covered by exactly one chunk; real searches now attach Amd 2 item 8 (Table 19), item 17 (Fig. 13), Amd 1 item 3 (Table 32). `covers` isn't embedded, so no re-embedding. The test is now strict: no amendment target may be uncovered.
